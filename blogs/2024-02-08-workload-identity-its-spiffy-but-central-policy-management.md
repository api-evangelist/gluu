<p>SPIFFY Mutual TLS (mTLS) is a way to secure workload identity and communication in a distributed system using the SPIFFE and SPIRE standards. (see also: <a class="app-aware-link " href="https://spiffe.io/">https://spiffe.io/</a>) SPIFFE stands for Secure Production Identity Framework for Everyone, and SPIRE stands for SPIFFE Runtime Environment. SPIFFE defines a platform-agnostic identity format and API for workloads, and SPIRE provides a system for issuing and verifying SPIFFE identities.</p>
<p>An East-West service mesh like Istio or Cilium could be a good place to enforce policies based on &#8220;workload identities&#8221; derived from the claims of the X.509 client certificate. Let&#8217;s say the policy is &#8220;version2&#8221; clients can&#8217;t call &#8220;version1&#8243; endpoints.&#8221; Thanks to <a class="app-aware-link " href="https://www.linkedin.com/in/ceposta?miniProfileUrn=urn%3Ali%3Afs_miniProfile%3AACoAAAMWH4UBw_-YAxeRzLxcvLeZfq_ikOQxqX4">Christian Posta</a> for the <a class="app-aware-link " href="https://www.linkedin.com/company/solo.io/">solo.io</a> webinar showing how in Cilium we could define a policy like this:</p>

<p>From an enterprise policy management standpoint, do I want network policies in my service mesh? It means I need to learn a one-off policy language. For example, Cilium has its way they express policies (see above). But <a class="app-aware-link " href="https://krakend.io/">KrakenD</a> uses the <a class="app-aware-link " href="https://cloud.google.com/certificate-authority-service/docs/using-cel">CEL</a> policy language. And there are a hundred other systems that might need to consume enterprise policies. Wouldn&#8217;t it be better to follow the lead of Kubernetes access control, and use OPA to manage policies, or some other PDP&#8211;pick from an increasingly vast array like <a class="app-aware-link " href="https://www.linkedin.com/company/axiomatics/">Axiomatics</a> , <a class="app-aware-link " href="https://www.linkedin.com/company/aserto-com/">Aserto</a> , <a class="app-aware-link " href="https://www.linkedin.com/company/permitio/">Permit.io</a> , <a class="app-aware-link " href="https://www.linkedin.com/company/sgnl-ai/">SGNL</a> ? Just to name a few&#8230;</p>
<p>We want the speed of decentralization, but the consistency and operational leverage of central control. <a class="app-aware-link " href="https://ebpf.io/what-is-ebpf/">eBPF</a> enables kernel-level optimizations and leaps forward in performance. But metaphorically, it doesn&#8217;t mean having a bunch of ACL&#8217;s in the router is the right thing, even if we can run those ACL&#8217;s faster then ever!</p>
<p>As an OAuth person, I see a lot of overlap between an MTLS <strong>workload identity </strong>(e.g. a &#8220;a kubernetes service account&#8221;) and an OAuth &#8220;client&#8221;. You can connect these two worlds&#8211;<a class="app-aware-link " href="https://datatracker.ietf.org/doc/html/rfc8705">RFC 8705</a> defines a mechanism to bind OAuth access tokens to a client&#8217;s mutual-TLS certificate, enabling endpoints to verify the access token presented was actually issued to the client presenting it. You could also achieve this with DPoP (<a class="app-aware-link " href="https://datatracker.ietf.org/doc/html/rfc9449">RFC 9449</a>), which might be better, because MTLS doesn&#8217;t work for mobile clients. The real edge is the super computer in people&#8217;s pocket.</p><p>The post <a href="https://gluu.org/workload-identity-its-spiffy-but-central-policy-management/">“Workload Identity”: It’s SPIFFY, but Central Policy Management?</a> first appeared on <a href="https://gluu.org">Gluu</a>.</p>
